# PS100 servo drive

How the Raspberry Pi drives the launch arm's PS100 servo over RS-485, what
has been confirmed on the real drive, and what is still open.

The Pi plans each throw, sends one relative move (distance + speed) over
Modbus RTU, and triggers it. The PS100 runs the servo loop itself. The
driver is `passer/hardware/ps100.py`; register numbers are in
`passer/hardware/ps100_registers.py`; the bench tool is
`python -m passer.tools.ps100_cli`.

## Wiring

RS-485 on the drive's communication connector (CN3/CN4, RJ45):

| RJ45 pin | Signal | USB-RS485 adapter |
|---|---|---|
| 5 | RS485+ | A (A+, D+) |
| 4 | RS485− | B (B−, D−) |
| 7 | GND | GND |

Leave the adapter's 5V and the other RJ45 pins unconnected (the same
connector carries CAN). A standard straight-through Cat 5/6 patch cable to
an RJ45 breakout works at 9600 baud; keep it short and away from the motor
power cables. If the drive doesn't answer, swap A and B.

On the Pi the adapter is `/dev/ttyUSB0` (CH340, `/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0`)
and the user must be in the `dialout` group (log in again, or reboot, after
`sudo usermod -aG dialout $USER`).

## Drive settings

`ps100_cli check` reads all of these and marks anything that differs.
Change them on the panel, save (long-press SET) and power-cycle.

| Parameter | Address | Needs | Meaning |
|---|---|---:|---|
| PA4 | `0x0004` | 0 | Control mode: position |
| PA11 | `0x000B` | 10000 | Command pulses per motor revolution (electronic gear 1:1) |
| PA14 | `0x000E` | 3 | Position command source: internal position |
| PA53 | `0x0035` | 1 | Servo forced on (no enable wire). The motor holds whenever the drive has power |
| P3-30 | `0x011E` | 1 | Virtual inputs driven by `0x011F` |
| P3-38 | `0x0126` | **28** | Virtual DI1 = internal-position start. The manual's RS-485 sections say 38: wrong for this drive (accepted, but nothing moves) |
| P3-39 | `0x0127` | 27 | Virtual DI2 = internal-position stop (the software stop) |
| P3-20 | `0x0114` | 16 | DO1 = positioning complete (bit 0 of `0x1010`) |
| P4-0 | `0x0200` | 1 | Internal position: relative |
| PA71 | `0x0047` | 1 | Modbus slave address |
| PA72 | `0x0048` | 96 | 9600 baud |
| PA73 | `0x0049` | 3 | 8N1 (0 = 8N2, the factory default) |

Also shown by `check`: PA20 (limit inputs ignored = 1), PA22 (speed command
source; 3 is the panel-jog setup, factory default 0), PA23 (max motor rpm),
PA40/PA41 (ramps), PA74 (on comms error: 0 keep running, 1 alarm and stop),
and P4-2..P4-4 (the move currently loaded).

**Must match the app config:** PA40/PA41 (ms per 1000 rpm) =
`launcher.accel_ms_per_1000rpm` / `decel_ms_per_1000rpm` in
`configs/rpi.yaml` (both 100 now). The planner uses them for the arm's
travel while speeding up and slowing down.

### Addressing

`address = group base + parameter number` (RS485 manual 1.4): PA at
`0x0000` (PA14 → `0x000E`), P3 at `0x0100` (P3-38 → `0x0126`), P4 at
`0x0200` (P4-4 → `0x0204`). The panel shows the PA group as `FA`; the quick
manual's `FC-n` input codes are P3-n. `ps100_cli read P3-38` reads by name.

Writing a parameter's address **saves it to the drive's EEPROM**. PA
parameters also have a RAM-only address at +`0x0080` (manual 1.6); none is
documented for P3/P4.

## A move

| Step | Register | Value |
|---|---|---|
| Whole motor turns (signed) | `0x0202` (P4-2) | e.g. 0 |
| Remaining pulses (signed) | `0x0203` (P4-3) | e.g. 2778 |
| Speed, motor rpm (> 0) | `0x0204` (P4-4) | e.g. 30 |
| Start: rising edge | `0x011F` (P3-31) | `0x0000` then `0x0001` |
| Stop (needs P3-39 = 27) | `0x011F` | `0x0002` |
| Done? | `0x1010` bit 0 | 1 = in position; drops to 0 within ~80 ms of a start, back to 1 when done (P3-20 = 16) |

`0x011F` is a bit field over the virtual inputs, `DI4 DI3 DI2 DI1`. Moves are
relative: motor position = P4-2 × 10000 + P4-3. Through the 10:1 gearbox,
10° of arm = 100° of motor = 2778 pulses. `kinematics.py` does the
conversion from arm degrees and arm rpm, using `launcher.gear_ratio` and
`pulses_per_rev`. `ps100_cli arm 10 --rpm 30` takes **motor** rpm.

The software stop is not an emergency stop. Don't rely on rewriting
P4-2..P4-4 during a move: the manuals don't say what it does.

## Status registers

Read-only, `0x1000`–`0x101B` (RS485 manual 1.5). `ps100_cli monitor` reads
them all in one request; `pos` reads the encoder position.

| Address | Meaning |
|---|---|
| `0x1000` | Motor speed |
| `0x1001`/`02` | Current position (low, high) |
| `0x1003`/`04` | Position command: stays 0 if the drive never starts a move |
| `0x1005`/`06` | Position error |
| `0x1007` / `08` | Motor torque / current |
| `0x1009` | Current control mode (PA4 codes) |
| `0x100A` | Temperature |
| `0x100B` / `0C` | Speed / torque command |
| `0x100D`/`0E` | Rotor position within one turn |
| `0x100F` | Input terminals (bit 0 = DI1; the virtual inputs show here too) |
| `0x1010` | Output terminals (bit 0 = DO1) |
| `0x1011` | Encoder input signal |
| `0x1012` | Bus voltage |
| `0x1013` | **Alarm number**, 0 = none |
| `0x1014` | Logic chip version |
| `0x1015` | Relay state |
| `0x1016` | Running state (values not documented) |
| `0x1017` | External voltage state |
| `0x1018`–`1B` | Encoder absolute position, 64-bit, low word first (with P3-37 = 0) |

Positions here are in **encoder counts, 131072 per motor revolution**
(17-bit encoder), not the 10000 command pulses per revolution used for
moves: a 2778-pulse move shows as 36411 counts.

Multi-word values must be read in one request: read word by word, a value
wobbling around zero can come back torn (−1 as 4294967295).

## When a move fails

1. `ps100_cli status`: times out → the link (A/B swap, PA71–PA73, `ps100.port`, `dialout`).
2. `ps100_cli monitor`: alarm number? Control mode 0?
3. `ps100_cli check`: fix every `FIX` line on the panel, save, power-cycle.
4. `ps100_cli read P4-4` after a move: not the speed you sent → wrong address (`ps100.address_offset: -1`).
5. `ps100_cli arm 10 --rpm 30` with the arm unloaded, then `monitor`:
   - `done` → working.
   - Motor moved, no completion → P3-20 = 16, or `ps100.completion_mode: time`.
   - Didn't move, `0x100F` DI1 went on, position command `0x1003` stayed 0 →
     the drive saw the start input but no start function fired: P3-38 must be 28.

## Bench status (2026-10-19)

Confirmed on the drive:
- Link: wiring and A/B polarity, slave 1, 9600 8N1, and the addressing rule
  (FA11 reads 10000, P4-4 reads back what was written).
- All settings in the table above; ramps 100/100 in both drive and config.
- Servo on (shaft holds), no alarm, bus 340 V, position mode.
- **First move:** with P3-38 = 28 (38 never started a move) and PA22 back
  to 0 (left at 3 from panel jog), 2778 pulses at 30 rpm moved the motor
  exactly 36411 encoder counts (10° of arm) in about 0.6 s, no alarm.
- **Direction:** a positive move turns the arm *backward*, away from the
  throw (the motor turns counter-clockwise seen from its front). The
  planner uses + = toward the throw, so `ps100.reverse_direction: true` in
  `configs/rpi.yaml` negates every move in the driver.
- **The app's back-to-back 0 → 1 trigger works** (two positioning moves of
  90° and 45° of arm at 30 rpm: 327682 / 327680 and 163844 / 163840 counts).
- **Completion is a level, not a toggle:** bit 0 reads 1 in position, 0
  from ~80 ms after a start until the move ends (bit 2 also drops while
  moving). After power-up it reads 0 until the first move completes.
  `completion_mode: level` waits for 0 then 1; the old `change` mode would
  have reported a throw finished as it started.

Open:

- **EEPROM wear:** every throw writes P4-2..P4-4 at their saving addresses.
  Ask the vendor for a RAM-only address for the P4 group, or how many writes
  the EEPROM is rated for.
- **Safety limits** (issue #2): PA23 is 5000 rpm (app limit 3000); PA74 = 0
  keeps running on comms errors.
